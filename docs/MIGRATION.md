# 从四个监控组件迁移到 Go

[返回 README](../README.md) · [统一后台](CONSOLE.md) · [架构](ARCHITECTURE.md)

## 新安装与已有安装

新示例使用 `central.monitoring.mode: native`。主服务器运行 Go 接收／检测／采集服务及 node_exporter，宿主机 systemd 管理进程负责可视化部署和看门狗。子服务器保留 Agent、Vector、exporter。

旧 YAML 没有该字段时默认 `legacy`。先仅升级主服务器，使统一后台与影子采集可用；旧 Prometheus、Alertmanager、Grafana、Loki 保持运行。然后在后台执行迁移，不能直接把旧 YAML 改成 native 跳过历史导入。

发布新版后，管理员在主服务器手动执行：

```bash
webscan --upgrade --central-only
```

本地构建或同步部署包不等于线上升级。后台必须开启才能使用迁移页面。迁移不改子服务器、通信协议、业务网站或防火墙。

## 迁移操作

1. 检查旧服务可访问、备份目录可写，磁盘有足够空间。任务预检需要数据大小两倍加 512 MiB 预留；数据和备份路径分别检查。
2. 系统设置 → “迁移至 Go 一体化模式” → 迁移历史并切换，进入部署任务查看进度。
3. 先一致性备份现有事件和指标 SQLite；备份失败停止。
4. 按保留期、时间窗口和固定项目指标导入 Prometheus；按项目标签导入 Loki，分页溢出时拆分窗口，任务记录检查点，重复导入按主键去重。导入使用持久化保护标记，实时采集暂不压缩未完成数据；失败或中断后标记保留，重试成功再解除。v2.0.33 使用新的指标检查点重放旧版导入，避免旧压缩过程遗漏字段。
5. 暂停新增 Loki 投递和旧健康通知，排空原 Loki 队列；新文件事件仍保存到事件库。
6. 导入最后增量并接管当前活动健康告警，保存核对计数与切换凭据。
7. 使用原镜像和节点身份重建中心，验证后台、事件查询和新鲜的主机指标；旧指标服务仍在时导入交接尾段。
8. 验收通过才停用本项目拥有的四个旧容器，并启用 Go 告警。复用的外部组件不停止；旧目录和部署回退记录保留。

迁移导入的是本项目展示用指标和文件事件，不实现任意 PromQL、LogQL 或 Grafana 插件，也不导入其他项目的数据。未知旧日志格式或无法完整读取的窗口会停止切换，不能静默截断历史。

## 保留的数据

网站、账号、网站故障历史、文件事件和飞书待投递消息继续使用现有事件 SQLite。服务器指标单独放在 `metrics-v1.sqlite3`；旧 Prometheus 和 Loki 数据目录保留。原有文件备份之外，日常中心备份也包含指标库。

默认 Go 原始指标 48 小时、5 分钟聚合 15 天；事件、投递记录、网站历史按各自保留设置清理。迁移完成后，在总览核对各节点、查一条已知历史事件，并在告警中心确认原有飞书消息仍可查询。

## 失败、恢复和回退

- 导入阶段失败：旧服务保留，原运行设置恢复；查看失败日志后重新提交迁移，已经完成的历史批次会跳过。
- 部署阶段失败：保留任务和原范围，通过部署任务恢复或回退，不能修改 YAML 或更换版本绕过未完成任务。
- 终端恢复通常使用 `webscan --resume --central-only`；回退使用 `webscan --rollback --central-only`。以该次日志里的实际范围为准。
- 回退恢复旧 Compose 和运行设置，重新启用本项目原服务；当前 SQLite 和已修改管理员密码保留，不用历史数据库覆盖新增事件。

切换完成后仍保留旧数据用于排查。不要先手动卸载四个组件，也不要删除旧目录后再尝试迁移。
