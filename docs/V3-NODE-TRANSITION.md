# v3 子控停写、备份、部署方式切换与回退

本模块仍处于本地开发阶段。已实现内部服务归属核对、停写控制、一致性快照、native／Docker 激活与恢复、双向部署方式切换及内核资源核对方法；**显式执行器已连接完整阶段，但实际安装验收仍不完整，不能用于生产升级**。公开部署写接口仍返回 `503 executor_unavailable`；默认 `node-v3` 只开放预检查和准备，`--lifecycle` 要求绑定完整配置包后选择服务阶段处理器。

当前实际验收：已发布 v2.0.34 Agent（真实 Compose）与两个活动旧 systemd 包装 sidecar，以及无包装的纯 Compose 三容器，分别在独立 x86_64 内核中切到 v3 native／Docker 并回退通过。纯 Compose 另已验证连续两次完整替换、后继回退，以及由独立新恢复任务继续恢复原三容器；原任务仍保持退役。保留原基线、当前数据库、各阶段事件与 JSONL 的原 ID，恢复原三个容器 ID 后旧 Agent 继续产生并导出事件。详细记录见 [验证记录](V3-VALIDATION.md)。上述结果仅证明这些组合的节点本地生命周期，不涵盖中心最终切换、旧 Vector 业务推送或完整安装器；后文单独步骤的测试不能代替整组结果。

## 服务归属与停写

服务名相同不代表归属相同。识别安装状态时先核对节点运行配置及固定数据目录，再核对具体服务：

- native：核对原生成单元、当前加载路径、无额外 drop-in、无待完成的 systemd 任务、加载状态、运行进程的程序路径及精确的 `agent --config <配置>` 参数；原 v2 单元必须匹配已知生成模板。存在额外启动／停止命令、需要重新加载或进程不匹配时拒绝操作。
- Docker：核对本机 socket、不可变容器 ID、Compose 项目及服务、镜像和启动命令；Agent 还核对数据及配置挂载。v3 容器核对生成定义中的完整挂载集合，包括监控目录只读权限及探针挂载，额外或重复挂载同样拒绝。
- 整组服务先完成核对，再开始停写。停止前再次核对；Docker 操作使用捕获的 ID，避免同名容器被替换后误停其他容器。只停已证明归属的服务，不删除容器、镜像或数据，不操作其他业务服务。
- 原启用状态、运行状态及 Docker 重启策略进入私有恢复资料。内部恢复方法保留原本停用／停止的状态，执行后重新读取实际状态；命令返回成功不能替代服务状态确认。

全新 native 环境不调用 Docker。既有 Docker 部署必须能访问原引擎，异常时明确失败。归属资料缺失时不会猜测；活动的旧包装 sidecar 仅由下述内部整组协调器按持久证据接管；普通单服务归属路径仍拒绝，不能仅凭识别模板就启停。没有包装且当前 Compose 已缺少定义、又无本任务退役证据的残留 sidecar 仍明确拒绝；完整纯 Compose 组按后文的捕获及恢复边界处理，已停用、停止的残留单元保持原样。Docker → native 即使缺少 Compose 也必须检查原引擎及容器归属，不能绕过。

### 旧 systemd 包装单元的只读识别

现已识别 v2 `InstallNodeSidecars` 实际生成的 Vector／node-exporter 包装模板，覆盖 HTTP、HTTPS、自定义指标端口、自定义镜像源及归档导入的镜像 ID。模板逐字比较，额外命令、重复配置、额外挂载、参数修改、环境变量和 systemd 占位符均拒绝；不把名称相同当作本项目服务。

旧部署将这些公开 unit 写为 `0644`，现采用单独的受限读取器兼容 `0600`／`0644`，不放宽凭据、运行配置和备份文件的私有权限要求。读取核对所有者、父目录不可由组／其他用户写入、普通单链接文件、大小、修改及变更时间和路径身份，拒绝符号链接、硬链接及读取期间变化。检查 systemd 状态后再次核对 unit 正文，整个过程不改写 unit、不调用 Docker、不启停服务。

只有匹配模板且已经停止、禁用、没有 drop-in、待执行任务或待加载变更的残留单元可以继续原有归属检查。未知 Agent 包装模板仍拒绝；失败且禁用、无进程的已知单元作为停止残留处理。普通单服务入口仍不接管活动或仍启用的包装服务；仅后文的整组生命周期可持久化捕获并操作，不能因识别成功就判为已经迁移。

原模板含 `ExecStartPre=-/usr/bin/docker rm -f ...`，启动它会删除并重建容器。因此不能简单在回退时执行原 unit 的 `start`，并声称原不可变容器 ID 已恢复。后文整组生命周期已补入包装服务的持久化停写、恢复、精确对象保留及中断续作；单独识别接口不会绕过此门禁。

隔离验证使用 `scripts/verify-v3-legacy-wrappers.sh`：一组无网络、只读根文件系统的 Linux 测试覆盖实际权限、归属及私有临时目录内的内部步骤，另一组调用真实 `systemd-analyze verify` 核对四份旧模板及两份保留 ID 单元。systemd 状态由替身提供，语法验证只用惰性依赖单元和 Docker 占位程序，没有启动真实服务管理器，不能作为实际停服、启动或回退验收。

### 包装服务的内部停写与原对象恢复步骤

私有 `legacyWrapperTransition` 提供单个 Vector／exporter 的捕获、停写、只读停写核对、恢复和只读恢复核对。**已由显式 v3 生命周期按整组证据选择，普通 v2 安装和公开 v3 写入门禁不变。** 调用方先通过 Journal 代次检查、核对并捕获整组服务，再停止第一个成员。

- 捕获核对源镜像实际 config ID、Linux amd64、镜像原入口和默认命令，以及完整挂载、传播方式、只读根目录、网络、用户、PID、能力、安全选项和日志限制。原容器必须没有 Compose／v3 身份，重启策略为原包装模板的 `no`；只有原 systemd 单元承担自启动。来源被改标、额外或重复挂载、未知选项、进程或运行配置变化均拒绝。
- Docker 会为宿主 PID 模式的 exporter 自动附加 `label=disable`。仅在此角色及模式允许该确切附加项，仍强制 `no-new-privileges`，拒绝重复项及任意 seccomp／SELinux 覆盖；捕获后完整实际选项继续进入对象指纹。挂载和安全选项的返回顺序规范化不改写原证据。
- 先将原完整单元、原运行／启用状态、容器及镜像证明和运行配置摘要原子保存到 `transitions/<任务>/wrappers/<固定服务名>/intent.json`。目录 `0700`、文件 `0600`；任务、节点、计划及目标配置绑定，旧代次由外层 Journal 拒绝。内容不进入后台任务或普通日志。
- 停写前持久化 `quiesce.json`，将原 unit 原子替换为按捕获的容器 ID 执行 `docker start --attach`／`docker stop` 的单元。明确执行 daemon-reload 并核对加载状态后，才禁用和停止服务。Docker 客户端已退出而容器仍存活时，只停止捕获的不可变 ID；不执行原 `rm -f`、镜像改标或按名称删除。
- 回退先持久化 `restore.json`，恢复原启用和运行状态。原本停止的对象保持停止；原本禁用但运行的对象恢复运行而不启用自启动。恢复后继续保留按 ID 启停的受管理单元，原删除模板只保存在私有意图中，避免下一次主机／Docker 重启删除旧对象。有效 unit 为 `0600`，不恢复危险的旧启动前删除命令。
- 恢复结果以 `restored.json` 绑定原意图；返回丢失后确认实际状态，不重复启动。已完成恢复后遇到外部服务或 unit 变化，只报告冲突，不重新修复或停服。捕获后尚未进入停写的失败只核对原状态，不授权修改外部变化。恢复开始后禁止该步骤重新正向停写。

本步骤不读写 Agent 数据库、Vector 私有缓冲、原 JSONL 或扫描规则，不执行 Docker 全局清理或网络规则变更。管理命令继承现有节点服务操作锁，超时仍按状态未知处理；只读核对不运行加载、启停或重启命令。

整组捕获、目标激活、双向方式切换后恢复及跨任务来源识别已连接下述内部步骤；真实 Linux amd64 systemd 的活动包装服务与正式旧 Agent 整组切换／回退已有上述联合验收；中断续作的整组故障分支仍以测试替身覆盖，不能据此判定完整生产迁移完成。

### Agent 与旧包装组件的整组备份边界

私有 `legacyWrapperGroup` 组合安装归属核对、两个包装服务的不可变捕获及现有 `transitionBackup`。支持一个原 native 或 Compose Agent，加一至两个已证明归属的旧包装组件；未识别的 Agent 包装单元、混合或缺失 Agent、其他活跃 sidecar 仍拒绝。显式 `node-v3 --lifecycle` 已按任务证据选择该协调器，公开 v3 写入仍未开放。

- 在节点服务锁和外层 Journal 代次保护下，先保存各包装组件的原 unit、镜像／容器证据，再确认原 Agent。主 capture 的 `installed.wrappers` 以固定服务名和 SHA256 绑定同任务私有意图；不会因后续 Compose 已不列旧 sidecar 就丢掉真实包装服务证据。
- 完整 capture 及配置、空间检查成功后，再写停服意图。每次首次执行和继续均重查整组归属、固定名称、原本停止成员、额外监督单元及成员检查点，才依次停 Vector、exporter 和 Agent。不确定的后续成员不能授权先停止前面的成员。
- 所有成员已停止且禁止自启动后，复用 Agent 写入锁、真实 SQLite 一致性备份及 JSONL／证书状态快照；重试保留原 capture 与快照，不将已停服务重新记成原始状态。损坏或缺失的成员意图不能作为无服务处理。
- 增加仅限目标尚未激活的整组恢复边界：任何激活目录、新 active 指针或最终回执均要求专用目标恢复，不能套用本分支。恢复前持久化门禁，重验整组；恢复原启用／运行状态，保持原容器 ID，不写当前数据库或原日志，不从旧快照覆盖新增事件。已完成恢复只做核验，不修复外部变化。
- 原单 Agent 支持判定及普通服务启停继续拒绝带 `wrappers` 的清单。目标驱动仅在同任务整组协调器核对通过后使用 Agent 视图；磁盘 capture 和摘要保留全部成员。

验证中的 SQLite、文件、权限和锁使用真实实现；Agent 与 systemd 命令状态仍为测试替身。该备份边界本身不处理已经启动的新目标，目标驱动使用后述专用恢复边界；跨任务来源识别见下一节。没有改动默认公开部署门禁，也没有生产操作。

### 保留 ID unit 的跨任务来源识别

第一次替换旧 unit 之前，将来源记录原子写入节点私有 `retained-wrappers/<固定服务名>.json`，绑定原任务、节点、计划、目标配置摘要、原 Spec 及首次私有意图 SHA256。目录 `0700`、文件 `0600`，只由服务端固定路径生成。来源记录不含原 YAML、令牌、SSH 私钥或可执行命令；原完整 unit 和对象证据仍在首次任务的私有意图中。

- 每次读取均验证目录、所有者、普通单链接文件、规范 JSON、原 Spec 与绑定摘要、首次捕获和停服凭据。引用必须直接指向首次 v2 模板捕获，拒绝引用链、循环、丢失、损坏、错节点或未知版本。
- 新任务对照该来源记录核对当前安全 unit、不可变容器 ID、完整对象指纹、运行配置、镜像配置 ID 和实际进程。镜像按已证明的 config ID 复查，不依赖可重新改标的来源别名。unit、挂载、策略、凭据配置或进程改变均拒绝。
- 新任务捕获自己开始时的启用／运行状态，写入自己的绑定与来源记录摘要；不会恢复成首次任务当年的状态，也不覆盖首次来源记录。新任务仅捕获后取消时保持按 ID 启停的 unit，不写回旧删除模板。来源发布后、unit 尚未替换的中断仅由原任务继续，不能被新任务认作空安装。
- 普通安装清单可识别已经停止、禁用且完整证明的保留组件，并将它们作为已停用残留单独核对，不要求它们具有 Compose 标签。返回清单前再次核对，以免 Agent 检查期间来源或状态改变后返回旧证据。活动或启用的保留组件仍要求整组迁移，普通单 Agent 路径继续拒绝。
- 受管理 unit 已缺失但来源记录仍存在时明确失败；不能把来源资料缺失当作没有旧服务。保留首次捕获及其停服凭据，不能先清理仍被来源记录引用的任务目录。已有 Docker 残留的 native 安装仍需原引擎可用以完成对象归属证明；全新 native 不调用 Docker。

该识别已接到内部组捕获和普通只读清单，不会自行启动服务或开放全组三容器升级。此前已在隔离真实 Docker 引擎验证两个厂商镜像对象被下一任务重新捕获、仍保留原 ID 和首次来源记录，systemd 状态使用替身。现另通过完整 x86_64 内核和真实 systemd 的单成员活动服务捕获／停用／恢复及跨任务来源验收；这仍不等于旧 Agent 与全部 sidecar 的联合迁移。

恢复活动包装服务时，systemd 的 `Type=simple` 可能先确认 Docker 附着客户端启动，容器仍短暂处于停止状态。恢复确认现在最多等待 15 秒，只读复查已捕获的不可变容器、完整对象指纹、unit、客户端精确参数和启用状态；等待不会再次发送启动命令。归属、unit 或启用状态改变立即失败，取消／超时不写完成回执。完成恢复的重复请求仍只核验，不修复外部变化。真实内核下的活动服务验收及其边界见 [内核工具](V3-KERNEL-VALIDATION.md) 和 [验证记录](V3-VALIDATION.md)。

### 整组目标切换与恢复边界

以上单成员和整组备份章节记录此前的接入边界。当前显式 `node-v3 --lifecycle` 已接入固定模板包装组件的整组预检查、备份、目标激活和恢复；普通 v2 部署、默认准备命令及公开 v3 写入门禁保持不变。

- 预检查采用独立只读观察，不发布捕获、不改写 unit、不启停服务。备份重新核对并保存原 Agent 与全部成员后才停写。各请求使用自己的驱动副本，后续阶段从任务 capture 重选协调器。
- 主 capture 和摘要保留全部包装成员。只有同任务协调器与成员证明有效时，目标驱动才可使用明确的 Agent 视图执行原 Agent 操作；普通主机启停方法继续拒绝忽略包装成员。
- 旧 native／Compose Agent 均可切换到 native／Docker 单 Agent。启动、续作及确认均复查包装组件已停止、禁用且 unit 已加载，拒绝未知监督服务及对象变化。
- 回退先停止并核对目标，按原 ID 将当前 SQLite 未确认事件导出为旧 JSONL，再恢复原配置和身份、停用目标。保留当前数据库及切换后事件。
- 首个旧组件恢复前，持久化 `restoration/group-resume.json`，绑定完整 capture、任务及恢复导出回执。只有原配置／指针恢复且目标退出后，才恢复成员和 Agent 的独立启用、运行状态。
- 恢复命令执行成功但响应丢失时，重试核对边界后继续剩余成员。投递可能已经恢复，因此不再次停止整组或重新导出正在变化的数据库。缺失／损坏回执、原库、unit、来源或异常目标状态均失败。
- 目标尚未激活时沿用独立整组恢复，不伪造目标或导出回执；Journal 可识别部分恢复及只读回退核对。全新 native 仍不访问 Docker。

文件、SQLite、锁和 Journal 使用真实实现；本轮服务管理器、Docker 和进程状态为替身，不等于真实 systemd／活动三容器安装验收，不解除正式发布和生产切换门禁。

## 先持久化恢复意图，再备份

内部备份绑定任务 ID、节点、计划摘要及配置摘要；接管时允许代次增加，但不能换节点、目标配置或计划。

1. 在停止服务前，将原服务状态、配置、规则、私钥、单元及原数据库是否存在的证据写入私有临时目录，校验后原子发布恢复意图。
2. 检查备份空间，停止已核对的写入服务，并确认已停止且禁止自启动。
3. 获取真实 Agent 的 `agent.lock`，如果仍有 Agent 占用锁则失败，不强杀未知写入进程。
4. 再次核对配置未发生变化，通过 SQLite 一致性备份接口生成独立快照，并检查数据库。
5. 保存 JSONL 及独立的证书吊销状态，写入包含大小、模式和 SHA256 的清单，逐级同步磁盘后原子发布。

重试复用首次持久化的服务状态，不能把重试时已经停止的服务误记为原本停用。已发布快照不能覆盖；文件变动、未列入清单的文件、链接或权限不符均拒绝。备份失败不能进入激活步骤。若原服务已经停止但尚未发布快照，可根据停服前的持久配置资料恢复原服务，并核对原本存在的当前数据库没有丢失；缺少原存在性证据时拒绝猜测。目标激活意图一旦存在，则禁止绕过缺失或损坏的快照。

```text
  quiesce.json            首次停服务前绑定已发布 capture 摘要
  activation/
    intent.json            目标配置指针、单元及原备份摘要
    legacy-import.json     v2 JSONL 对账完成凭据，绑定任务及快照
  restoration/
    intent.json            恢复绑定
    export.json            已持久化补发阶段及数量
    no-effects.json        未进入停写的失败备份安全结束凭据，与上两项互斥
```

目录为 `0700`、文件仅服务账号可访问；实际子控要求 root。恢复资料含私钥及旧推送凭据，不返回后台接口、任务结果或普通日志。没有执行在线数据库压缩；一致性备份只写新快照，不改写原数据库。

## 纯 Compose 旧三容器的内部整组迁移

无旧 systemd 包装服务时，私有协调器可捕获同一 Compose 项目中的旧 Agent、Vector 和 node-exporter。普通单服务路径不获得接管活动 sidecar 的权限；混合管理、缺少原 Compose 定义或未知服务管理器仍拒绝。检查真实 systemd 的已加载旧单元，也拒绝仅存在于发行版目录、而非 `/etc` 的旧包装服务。

- 主 capture 使用独立 `installed.sidecars`，绑定 `transitions/<任务>/sidecars/<固定容器名>/intent.json`，不伪造包装 unit。证明包括 Compose／运行配置摘要、实际镜像 config ID、完整容器设置、原运行状态和重启策略。复用已知厂商参数与挂载校验，始终保存实际身份。
- 先捕获整组，持久化停用凭据，再禁用重启并只停止原不可变 ID；重启策略、运行状态分别恢复。停止或启动已发生但响应丢失时核对实际状态再续作；取消不能写恢复完成凭据，已完成回退也不能借重放修复外部漂移。
- Docker 转 native 的旧 Compose 文件按原生命周期退役。缺失只在捕获、快照和 native 激活意图完整绑定、原 Agent 仍停用并保有退役名称时接受；文件存在但内容变化始终拒绝。核对不依赖目标新配置或证书仍可用，保留损坏后回退能力。
- 停用 sidecar 的豁免仅由当前生效指针的原始捕获或已捕获的前驱指针证明；沿受校验配置链查找，不按名称、停止状态或任意任务目录猜测。v3 native 后续检查也核对这些旧对象，发现重新运行、替换或丢失即失败；全新 native 不调用 Docker。
- 数据库、JSONL 对账、待确认事件导出与恢复共用既有实现，不读取 Vector 私有缓冲、不覆盖当前数据库，不清理原容器、镜像或业务数据。

测试替身覆盖两种目标、独立原状态、响应丢失、证明损坏、取消、外部漂移、后继捕获和目标配置损坏后的回退；真实内核模式为 `pure-compose`。实际通过结果与范围以 [验证记录](V3-VALIDATION.md) 为准；中心联合安装、公开部署提交和正式发布门槛继续关闭。

后续补充的内部活动指针以可选 `capture_sha256` 绑定整份捕获清单；新任务缺少捕获或内容变化即失败，不再降级为未迁移状态。历史遍历只沿捕获中的前驱指针，校验配置／定义摘要、任务、快照与激活意图，最多追溯 128 层并拒绝循环，超限或资料缺失明确停止；每个历史 Docker Agent 必须保持原不可变 ID、退役名称、停止状态及关闭自启动。检查不会擅自修复漂移。早期开发态中已落盘、未带此字段的激活意图保留原编码，以便中断任务继续。此类未带摘要的当前指针仅在首层捕获意图不存在时保留原兼容行为，不作为新迁移的恢复证明；历史层缺失、已存在的捕获损坏仍拒绝。恢复路径也核对新增摘要的一致性，同时不依赖损坏的新运行配置。

真实内核用例已扩展为两次完整服务替换及逐级回退，覆盖更改配置版本、历史 Agent 策略漂移拒绝、当前数据库与各阶段原事件 ID。夹具扩展本身不代表验收通过，实际运行结果以 [验证记录](V3-VALIDATION.md) 中的对应后续记录为准。

本轮增强验收仍失败：native 后继替换及回退完成后，原任务已被 Journal 永久退役，直接请求其 `restore` 返回 `remote-conflict`。这是旧请求防重保护，不能以调高代次或移除栅栏绕过。仍需独立恢复任务绑定原任务、捕获摘要、当前完成的回退及当前生效指针，并接入主控租约／审计后重跑；Docker 分支及完整逐级恢复尚无本轮通过结果。

## native 激活与恢复

内部 native 单服务方法支持全新安装、已确认归属的 native 原服务，以及只有一个 Agent 的 Docker 原服务。整组迁移必须附加前述协调器和同任务完整成员证据；未附加时仍拒绝活动旧 sidecar，不允许只切换 Agent。

- 激活前验证已准备的程序、配置及原快照，在持久意图中绑定任务、计划、原配置、快照摘要和目标单元。
- 修改文件前获取 Agent 写入锁；仅在原内容或本任务目标内容之间原子替换单元及 `active.json`，不覆盖未知文件或符号链接。探针只能建在已有监控目录下，不创建业务目录。
- 加载单元，启动唯一目标服务，再核对单元路径、进程、精确参数和启用状态。响应丢失后若同一目标已运行，只确认状态，不再次启动。
- 恢复前持久化意图，停止已证明归属的服务，按当前数据库导出待确认事件，再恢复原配置指针、单元及原启用／运行状态。原本停止或禁用的服务不会被强行开启。
- 目标二进制或新配置损坏时，恢复仍可使用意图中保存的单元证明归属；原配置若被其他操作修改，则停止并提示冲突。同版本同配置的操作也以任务指针区分恢复状态。
- 完成恢复后不允许重新执行本任务备份或正向激活。不恢复旧 SQLite 快照，不覆盖证书吊销下限，不移除已产生事件。

备份、激活、恢复及补发共用 `service-operation.lock`。变更状态的 `systemctl`／Docker 客户端继承锁描述符；调用方超时或退出后，客户端未结束时下一操作仍无法获取锁。超时报告状态未知，不能当作“没有执行”。实际服务状态仍需重新核对，继承锁不等于已证明外部管理器所有任务完成。

## 内部持久化阶段编排

新增独立的内部 native 阶段处理器，将预检查、准备、备份、激活、本机验收、完成回执、恢复及回退验收接到现有子控 SQLite `Journal`。默认 `node-v3` 命令使用预检查／准备处理器，显式 `--lifecycle` 选择完整处理器；公开部署接口仍关闭。

- 预检查即核对原安装归属；只允许 native 或单 Agent Docker 原安装，混合原安装和活动旧 sidecar 不能接管。
- 中断后先取得服务操作锁，再核对原持久资料、实际服务和阶段文件。活动客户端仍持锁时返回未知；不得仅凭 SSH 断开就重复变更。
- `absent` 表示该阶段尚未完成且已证明可以按持久意图安全续作，并不保证没有产生过中间文件。已完成阶段再次读取时重验相关文件和服务，不能只依赖数据库中的完成标记。
- 切换中的 daemon-reload、enable、start 响应丢失后可补齐记录；已运行的目标不会再启动一次。只读资源验收失败后仍可进入保留当前数据的回退。
- 本机完成回执绑定任务、计划、配置及激活摘要。它只代表本机阶段完成，不能推进中心 `applied_version`；主控现已加入实际采集器的 mTLS／版本／指标／事件证据门禁；规则、覆盖及正式执行器仍需接通。

当前编排验证使用真实 SQLite、私有文件与进程锁，服务管理和资源证据为测试替身。尚不等于原生 systemd 安装器已完成实际验收，也没有开放 Docker／旧三容器迁移。

## 内部 Docker → native 切换

native 阶段处理器现可接管已确认归属的单 Agent Docker 原服务，包括旧单容器及原 v3 安装。该分支已由显式 SSH 执行器选择；后台部署提交仍未开放。

- 先完成捕获、原服务停写与一致性快照；激活意图落盘后，按保存的容器 ID 核对原对象、名称和重启策略。修改、丢失对象或名称冲突均停止操作，不清除冲突容器。
- 原容器停止且关闭自启动后改为任务绑定的保留名称，再写入 native 单元与配置指针。native 已运行时还要求原 Docker 对象处于保留名称、停止及禁止重启状态，防止两个写入者。
- 旧单容器的生成 `compose.yml` 已在 capture 中完整保存；核对原内容后移出活动路径，使切换完成后的 native 归属检查不再依赖 Docker。原主 YAML、不可变 v3 配置、容器、镜像及数据不删除。
- 回退停止 native、从当前 SQLite 导出待确认事件，恢复原生成配置、原容器名称及指针，并恢复原运行状态和重启策略。原本停止的容器保持停止。原容器已恢复运行但响应丢失时只确认结果，不再停止或启动。
- 未记录激活意图时不接管已经改名的原容器；原配置变更、原对象误启用、并发写入和配置／名称冲突均失败，不能覆盖外部修改。

真实 SQLite Journal 和服务管理替身已验证正常阶段、资源失败回退、捕获后快照前中断、改名及启动响应丢失、旧 v3 精确对象与指针恢复，以及新增事件保留。本分支未完成真实 systemd 运行环境验收；上一节及 Docker 专节的真实引擎验证只覆盖 Docker → Docker，不能作为跨方式切换成功证据。反向切换的私有实现见下一节；旧三容器接管仍需继续实现。

## 内部 native → Docker 切换

Docker 阶段处理器现可接管已确认归属的单个 native Agent，包括旧 native 和原 v3 安装。显式阶段命令可以选择该分支；部署写接口仍未开启。

- 捕获原单元、配置、原启用／运行状态及一致性数据库快照；只有绑定本任务、原捕获与快照摘要的激活意图，才能授权移出原单元。
- 原服务必须已经停止、禁用且无待执行 systemd 任务。核对原单元内容、权限、加载路径和进程归属后移出活动路径，再执行 daemon-reload；只有系统管理器确认无该单元、无进程、无需重载时才创建和启动 Docker 目标。缓存中的旧加载状态只能用于继续操作，不能判为切换成功。
- 新容器仍按独立任务项目、镜像摘要、精确挂载、持久对象 ID 及创建回执核对，避免重试重复创建。目标运行期间继续要求旧 native 单元已退出活动路径且不会自动启动。
- 回退按持久 ID 停止目标，从当前 SQLite 导出未确认事件，保留故障容器。原单元通过同目录私有暂存、校验和无覆盖原子发布恢复，再恢复原配置指针、加载单元及原启停状态；不覆盖当前数据库。已有 v3 原服务恢复原任务指针及精确程序／配置。
- 恢复启动或启用成功但响应丢失时，仅在原单元、原指针及目标已停止且禁用的边界认可原服务。已完成恢复直接确认，不重复停止或启动。缺失激活意图不能接管已经移出的单元；外部单元、drop-in、权限或进程变更以及并发写入均拒绝。
- 新程序、运行配置或 Compose 损坏时仍能按保存的对象证据回退。捕获后快照前失败可依原捕获恢复；已进入目标激活后缺少快照则不能绕过。

本组使用真实 SQLite Journal、配置及补发文件，systemd／Docker／内核证据由测试替身提供。覆盖完整阶段、重开及响应丢失、原服务各种启停状态、原 v3 指针恢复、资源失败、配置损坏和新增事件保留。它不替代真实 systemd 跨方式验收，也不代表正式安装器已交付。

## 停写前失败与损坏进程

备份开始先写入任务绑定的 `backup-attempt.json`；首次停止服务前另将 capture 摘要持久化到 `quiesce.json`。原服务在预检查后被外部操作修改，导致尚未建立 capture 就失败时，可证明本任务没有进入停写，再写入独立的无变更恢复凭据结束任务。此分支不运行 systemctl／Docker，不覆盖外部修改，不停止或重启任何服务。

无变更恢复要求尝试凭据完整且绑定本任务，capture、停写意图、快照和激活资料均不存在。已有停写意图而 capture 丢失时必须报未知，不能把遗失恢复资料当作没有执行。凭据损坏、换计划和符号链接均拒绝。完成此恢复后，本任务不得重新进入备份或激活；响应丢失按持久凭据补交结果。旧的、没有该尝试协议证据的异常目录不能自动套用此分支。

已删除可执行文件但仍运行的进程，仅可凭精确程序和参数证明归属后停止。目标激活、资源验收及原服务恢复完成检查要求可执行文件仍有效，不能把 `/proc/.../exe` 的 ` (deleted)` 状态判为健康。

## Docker 本机只读验收

内部 Docker 验收方法按不可变容器 ID 核对项目身份、镜像、精确程序和参数，以及生成配置中的完整挂载集。资源要求绑定已经校验摘要的服务定义，不能同时调低“期望值”和容器限制绕过检查。

验收核对引擎已加载的 CPU、内存、文件句柄和 Go 参数，以及运行、重启、暂停、OOM、用户、只读根目录、能力和网络隔离设置。前后读取 PID、启动时间及重启次数，检查过程中容器或资源发生变化则拒绝。输出仅包含必要证据，不返回环境变量或原始 inspect 内容。

进一步读取宿主机 `/proc`，证明实际运行的是目标程序和配置；cgroupfs 或 systemd 驱动必须包含完整容器 ID，再通过与 native 共用的内核读取器检查 CPU、内存和句柄。PID 重用、控制组变化、已删除程序、无限制或缺失证据均拒绝。

真实隔离容器已验证 Docker 加载值及运行中修改内存限制的拒绝；v1／v2、两种控制组驱动及进程变化使用文件和进程证据替身验证。独立受限 Linux 容器验证共享内核读取器，不代表宿主机上的完整 Docker Agent 归属或服务切换已经验收。

## 内部 Docker 激活及恢复方法

已增加内部方法，支持全新 Docker 安装、已确认归属的单 Agent Docker 原服务，以及上一节说明的单 native 原服务。活动旧 sidecar／包装服务仍不在此方法支持范围内。方法已接到子控 SQLite Journal 及显式 SSH 执行器，公开部署接口仍关闭；当前不允许生产调用。

- 激活意图绑定原配置、已完成的一致性快照、目标镜像配置 ID、任务和目标配置。先证明原容器已停写且关闭自启动，将它改为本任务的保留名称，再创建新容器。
- 每个任务采用独立的 Compose 项目，复用已校验的单服务定义；禁止构建、拉取和替换旧项目容器。任务项目、容器 ID、完整挂载及配置均需核对。创建结果在启动前持久化；再切换配置指针、启用目标并确认运行。
- 创建、重命名、设置策略和启动的响应丢失后按实际对象继续，不重复创建或启动。已记录的目标缺失、名称冲突、被改名但未记录的目标及重复任务对象均报未知，不把它们当成可以重建的空安装。
- 恢复停止已证明归属的目标，按当前 SQLite 导出待确认事件，再将目标改为故障保留名称、恢复原容器名称及原配置指针；旧数据库快照仅作为证据，绝不替换当前数据库。基线更新、任务、已确认状态和证书吊销下限保留。
- 原容器的运行、停止及重启策略按 capture 恢复。原服务已成功启动但响应丢失时，只确认恢复结果；不会再次停写或重建它。没有发布快照且尚未激活时，可依 capture 恢复。
- 已有目标对象凭持久 ID 及指纹恢复；目标程序、运行配置或 Compose 文件损坏不要求重新验证新程序才能回退。容器身份、快照或持久记录损坏则拒绝操作。

专项测试使用真实 SQLite、文件及操作锁，覆盖旧 Docker、旧 v3、同程序／配置的不同任务、确认丢失、部分恢复及新增数据保留。内部 Docker 阶段处理器还覆盖 Journal 重开、递增代次、已完成回执重验、活动客户端锁、损坏证据拒绝及无变更恢复。没有创建回执的目标只允许仍处于从未启动的 `created` 状态；运行或已退出的对象均不能被当成丢失创建响应接管。

独立嵌套 Docker 引擎已实际执行程序／配置／镜像准备、Compose 创建、停止和启动、同配置不同任务切换及精确原容器 ID 恢复。实际 Agent 完成 mTLS 配置回执并采集文件事件；启动成功后故意丢弃响应，Journal 续作保持 PID／启动时间不变。实际调高内存限制造成验收失败后回退，备份后新事件仍保留且完成补发导出。环境预检查在该用例中由替身提供，不代表正式安装预检查已经贯通。

真实引擎还暴露 Docker `Mounts` 返回顺序不固定的问题：指纹现使用副本按挂载路径、来源、类型和读写位排序，不改写原证据，不忽略重复或变更的挂载。尚未完成原生 amd64 宿主机上的完整 Agent 进程／内核成功验收、正式节点验收和旧三容器接管，不能据此认定 Docker 安装器已交付。

## native 资源验收

新增内部只读验收方法，要求目标激活意图、准备文件、单元及运行进程一致，随后分别核对：

- systemd 当前加载的内存、CPU、文件句柄及资源记账属性。
- `/proc/<PID>/limits` 中的软／硬文件句柄限制。
- `/proc/<PID>/cgroup` 和挂载信息所指向的真实层级，支持统一 v2 及 v1／混合挂载；不猜测 CPU 控制器目录。
- 内核的内存硬上限及 CPU 配额／周期。无限制、错误层级、缺失控制器、无效数值或权限失败均不能判通过。
- 验收前后进程启动计数、成员关系及最终 PID，防止读到进程替换前后的混合证据。

本地资源核对仍不等于中心采集验收。主控已加入实际采集器的网络、加载版本、指标和事件证据门禁，详见 [部署状态](V3-DEPLOYMENT-STATE.md)。目录覆盖、扫描就绪、实际服务管理和正式执行器仍未全部接通。

## v2 JSONL 启动前对账

内部 native／Docker 激活在取得服务操作锁及 Agent 写入锁、证明原服务停写之后，从本任务已校验的一致性快照读取旧日志，再允许目标启动。这一步已经接入显式生命周期处理器；它是旧部署兼容的前置能力，**不代表活动 Vector／exporter 或旧 systemd 包装单元已经可以接管**。

- 仅处理旧 Vector 实际读取的顶层 `events-*.jsonl`。其他诊断日志保持原样，不解析 Vector 私有缓冲，也不移动或删除原日志。
- 原 SQLite 已知 ID 以原记录为准，保留原 payload、确认状态、永久拒绝、导出标记、基线及扫描任务。日志独有的事件按原 ID 补入当前数据库，等待主控采集确认，不恢复旧数据库覆盖当前数据。
- 新补入事件在不同日志中重复时，允许等价 JSON；同 ID 的内容冲突阻止启动。比较保留整数文本精度，不把大整数转换成浮点数。原始日志及快照仍保留，不能静默丢弃冲突正文。
- 单事件最多 2 MiB，每事务最多 100 条、输入不超过 4 MiB。`nodeops_legacy_imports` 在当前 Agent SQLite 记录绑定任务、计划、配置、快照及文件摘要的字节游标；事件补入与进度在同一事务提交。断线或写入失败后从已提交游标继续，未提交批次不计为成功。
- 全部文件处理后原子保存私有 `activation/legacy-import.json`。回执发布前中断可从 SQLite 完成游标重建；已存在但损坏或不匹配的回执不能当作“尚未处理”。激活响应丢失、本机验收及完成阶段均重新要求有效回执，不重新启用或启动目标。
- JSON 损坏、身份不符、重复身份字段、空行、超限、链接、快照或游标变化、缺失当前数据库均阻止目标启动，不从旧快照猜建新数据库。失败前已提交的补入保留；回退继续从当前数据库导出待确认事件。

文件来源、游标和完成资料都由受控阶段生成，不增加路径上传接口。Agent SQLite 只新增兼容的辅助表；中心 schema 保持 27，v2 运行流程不变。此前内部开发任务若已启动目标但没有此对账凭据，会拒绝进一步确认，应按原任务回退核实，不能手工伪造完成回执。

隔离验证命令为 `scripts/verify-v3-legacy-reconciliation.sh`。该脚本使用只读根文件系统、独立临时目录和 `--network none`，不读取生产配置或启动通知工作器。它验证真实 SQLite 分批／续作、原 ID 和确认保留、原日志不变，以及当前真实 Linux Agent 构造、重启补读和确认。服务管理证据使用替身，尚未启动实际 systemd／Docker Agent，也不替代 mTLS 网络、旧三容器或完整安装验收。

## 回退补发保留新数据

内部回退导出方法只在已证明服务停止且持有 Agent 写入锁时工作。它验证原备份后读取**当前** SQLite，不将旧快照恢复到当前数据目录。

- 导出全部未确认事件，包括备份后新产生的事件和已有永久拒绝记录；保留原事件 ID。已确认事件不重新导出，也不改写其确认状态。
- 每批最多 100 条、4 MiB，单事件最多 2 MiB；核对事件及节点身份。JSON 紧凑化保留整数文本，不经浮点数转换。格式损坏或身份不符会中止本次恢复并保留原记录，不能静默跳过或删除。
- 生成兼容旧 Vector 的 `events-v3-rollback-*.jsonl`。先写临时文件、同步、无覆盖原子发布并同步目录，再事务登记 `logfiles` 和事件的 `exported` 字段。
- 文件名绑定任务和内容摘要。文件已发布但事务失败时，重试验证并复用该文件；不覆盖异常文件。即使已有导出回执，只要原服务尚未恢复运行，续作仍会核对当前待确认事件的补发文件：缺失则从当前数据库重建，损坏则停止恢复。部分批次失败时保留已完成批次，并报告实际完成数量。
- 不修改基线、扫描任务、原始 payload 或确认状态，不覆盖当前证书吊销下限，不提前启动旧投递器。中心仍按事件 ID 幂等去重。

native 的配置／单元恢复、Docker 原对象及名称恢复已有内部实现；中心代次、新旧协议验收及正式 SSH 部署仍需由完整运行器接通。

## 当前验证与边界

本地测试覆盖原服务状态、错误归属、额外挂载、先核对全部服务、备份失败续作、真实 SQLite 快照、符号链接、损坏清单、磁盘空间不足、原配置变更、写入锁，以及回退导出的分批／事务失败／重试和新增事件保留。

显式隔离 Linux 测试使用真实 Agent 和扫描工具，验证实际写入锁、快照、补读、确认及补发。新增子进程用例实际执行本次编译的 CLI、mTLS、文件采集和 SIGTERM 退出；服务管理仍为测试替身。

本机 Docker 为 ARM 虚拟机，amd64 通过 Rosetta 执行。严格的原生进程归属用例在此环境明确跳过；独立命名的转译用例仅在测试替身中适配转译器程序路径，生产校验不接受转译器替代目标程序。不能把转译运行记作原生 amd64 归属验收。

独立容器设置 256 MiB、1.25 CPU 和 65536 文件句柄限制，验证真实内核读取；另用真实 `systemctl` 客户端及不响应的测试总线验证锁继承。这些内核及锁用例**不是实际 systemd 服务安装、资源落地或三容器迁移验收**。Docker 的真实切换证据仅限前述独立嵌套引擎用例，不含成功的完整内核验收和正式安装流程。

完整本地回归见 [验证记录](V3-VALIDATION.md)。中心已增加目录根监听、规则绑定、Agent／扫描心跳及启用引擎自检门禁：verify 后新样本变坏，finalize 也会拒绝。真实 Agent／YARA／inotify／mTLS／PG 用例已验证此行为；扫描自检不创建业务事件；另有实际私有 clamd 自检和停服失效验证。完整探针与跨部署方式扫描验收仍待完成。

正式发布前仍须完成实际服务管理环境验收、正式 SSH／主控阶段编排、Docker 完整成功验收、旧部署兼容和正式命令／网页接入；其余 v3 缺口见 [重构进度](V3-RECONSTRUCTION.md)。

## 后继回退后的独立恢复任务

子控内部生命周期增加独立恢复任务，解决连续升级后需要继续恢复更早安装的问题。后继任务回退只恢复安装状态，不恢复旧任务的执行权限；旧任务即使提交更高代次，仍返回 `remote-conflict`。

- 新任务只允许 `restore`、`verify-rollback`。引用固定的原任务与计划、原 capture 摘要、当前安装指针摘要，以及已完成回退的后继任务与计划，不接受路径或命令。
- Journal 接管前要求原任务已完成并退役、未开始恢复；当前后继未退役、已完成回退且无运行阶段。随后在服务操作锁内核对实际安装、原备份及后继回执，错误证据不能先取得任务权限。
- 检查不会启停服务或写恢复意图。首次执行在私有 `transitions/<新任务>/recovery/intent.json` 持久化完整授权，再调用原 capture 对应的恢复驱动；目录 `0700`、文件 `0600`。原 Journal 身份保持退役。
- 响应丢失后由新任务继续，复核不可变证据及原驱动的部分恢复状态；不从旧快照覆盖当前数据库。完成后的重复检查只验证，不重复启停，也不修补损坏凭据。
- 后继本身可以是恢复任务，逐级验证其不可变引用，拒绝循环并限制链深度为 128。任一中间凭据损坏，外层已完成恢复也不能继续报告验证通过。

本地测试使用真实 SQLite、私有文件、快照和 Journal；服务管理替身覆盖新身份接管、旧任务隔离、响应丢失续作、元数据漂移、符号链接及连续两级恢复。实际 Linux 验收结果见 [验证记录](V3-VALIDATION.md)。

主控现已补入正常完成阶段的可信安装证据保存：子控在操作锁内校验原 capture、快照和激活目标，将 capture 与目标指针摘要返回；SSH 将原请求 Spec 与证据绑定，PG 在同一终态事务中保存独立密钥认证的记录。读取使用不可变配置快照，不回读较新草稿，详见 [主控证据](V3-DEPLOYMENT-STATE.md#安装完成的可信恢复证据schema-28)。新回执有真实 SQLite、文件、Linux root 及 PG／SSH 测试，但尚未重新运行完整内核安装验收。

主控 schema 29 已增加本地管理员专用的新恢复任务入口，使用独立密钥认证来源和后继，绑定当前运行代次、备份引用及 SSH 请求。恢复时使用原安装 Spec 和当前可信辅助程序，拒绝上传前向部署用的配置、镜像或程序包。支持后继本身为恢复任务的逐级核对；当前已保存草稿保持不变。见 [恢复工作流](V3-DEPLOYMENT-STATE.md#历史安装的独立恢复任务schema-29)。公开部署写入门禁继续保留；配置应用父任务协调及主控联合真实服务验收尚未完成，不能据此宣布完整 v3 已交付。
