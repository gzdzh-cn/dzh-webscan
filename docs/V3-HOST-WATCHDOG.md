# v3 独立宿主看门狗与运行证据

本文对应 2026-11-01 的本地实现。发布、生产升级和旧数据导入分别授权；本说明不表示线上已经安装或完成灾备切换。阶段验收以 [迁移实施记录](V3-FEATURE-MIGRATION.md) 为准。

## 职责与边界

看门狗是单中心宿主上的独立 Go/systemd 服务，使用独立 SQLite 保存观测、通知出箱、发送尝试、通道额度及设置核验检查点。API 或 PostgreSQL 暂时不可用时，已确认并加密缓存的通知配置仍可用于宿主故障通知；没有已确认配置、密钥不可用或事务结果不明时暂停发送。

它检查固定安装资料中的四项组件：

| 组件 | 实际检查 | 不代表什么 |
|---|---|---|
| API | 固定回环地址的 `/healthz` | 不等于全部后台业务均已验收 |
| PostgreSQL | 使用受限宿主配置发起数据库连接检查 | 不等于备份可恢复或所有查询正常 |
| VictoriaMetrics | 固定回环地址的 `/health` | 不等于历史完整或容量已经认证 |
| 存储 | 看门狗、PG、时序库数据目录所在文件系统的空间和 inode | 不等于各目录自身的文件占用 |

可用空间低于 256 MiB，或有 inode 计数时可用 inode 少于 128，记录存储异常；三个目录的文件系统证据不完整则保持未知。内核、启动标识、运行时间和总内存来自宿主 `/proc` 与系统调用，不从 API 容器推测。

每轮探测结束后等待十秒再开始下一轮；启动前三分钟只积累观测，不生成故障状态切换通知。连续三次异常产生故障，连续两次正常产生恢复；未知不会变成正常。维护抑制只针对明确组件，最长十五分钟，到期自行失效，不改写实际健康证据。

看门狗不会自动重启中心、PG、时序库、Docker 或业务服务，不修改防火墙。宿主自身断电、整机断网等故障可能同时阻止本机通知，独立宿主服务不能替代外部可用性监测。

## 安装、信任和升级

新的 format 3 单中心安装默认准备并启用看门狗。已有安装未配置时继续显示未知，不因升级网页自动添加宿主权限或伪造正常状态。

宿主配置项为 `host_watchdog.enabled`、`socket`、`state_directory`、`spec_file`。受管理安装默认将状态放在 `<安装目录>-watchdog-state/watchdog.sqlite3`，socket 放在 `<安装目录>-watchdog-run/control.sock`；实际路径以已验证资料为准。状态目录与 socket 目录分离，权限 `0700`，数据库及 socket `0600`。服务以 Linux root 运行，只接受同一 UID 的 Unix socket 对端，并验证 Vault 派生的消息认证码及请求时间。

宿主支持资料绑定原 `install.json`、受发布签名保护的新程序、宿主配置的摘要和实例身份。API 只接触必要配置、原 Vault 及私有 socket；不把 CA 私钥或 Docker socket 挂入 API。浏览器只读取 `/api/v3/dashboard` 的安全投影，没有公开探测、任意命令或私有 RPC 接口。

已有中心使用独立目录的升级叠加资料。`preview-single-web-upgrade`／`prepare-single-web-upgrade` 请求可明确设置 `host_watchdog: true`，并提供原 `installation_file`；原安装已启用时延续其状态目录和绑定。准备结果包括认证的 `watchdog.json` 与独立 `watchdog.service`，不自动停止服务或执行数据库迁移。维护时先核对来源与目标文件摘要、备份并显式升级数据库，再由管理员安装核验后的 unit 和配置，验证实际宿主观测。完整中心升级流程见 [单中心安装与升级](V3-SINGLE-INSTALL.md#已有单中心升级模板)。

不能覆盖原不可变安装记录、重新生成 Vault/CA，或直接替换原安装程序来消除校验失败。PKI 和备份维护工具各自固定程序版本及摘要；数据库结构升级后必须同步准备兼容的独立维护资料。PKI 使用专用维护升级包，见 [独立证书维护升级](V3-SINGLE-INSTALL.md#独立升级证书维护程序)。旧备份策略和旧 timer 也不能通过原位修改签名绑定冒充新版；升级资料、当前数据库结构及实际执行程序必须一致，冲突时停止并保留原资料。只升级网页不等于完成宿主维护升级。

## 通知额度与结果不明

已启用看门狗配置时，中心普通通知、测试通知和宿主通知通过同一宿主 SQLite 领取额度，按通道及当前已确认运行版本核对。飞书同时遵守秒级及分钟级限制，邮箱遵守分钟级限制；额度不能因 PostgreSQL 故障改为无限发送。请求使用稳定尝试标识，重复领取不获得新额度，授权仅短时有效。时钟明显倒退时停止释放新额度。

设置应用先冻结宿主发送，再核对 PostgreSQL 事务实际提交／回滚状态、数据库身份、版本及摘要。只有证据一致才启用对应配置；断网、响应丢失或事务结果不明保持冻结，工作器可根据持久检查点继续核验。保存草稿不会偷偷切换正在使用的通道。密文使用原 Vault 加密，不将收件凭据或原始通道响应放入公开状态。

发送前先持久记录尝试；进程中断或发送响应不明记录 `unknown`，不自动当成尚未发送重新投递。`accepted` 只表示发送器接受，不代表收件人已读。数据库恢复可用后，按稳定标识把安全历史投影同步回中心，确认中心事务保存后才标记已同步；不向网页暴露原始回执。

## 总览如何判断

`GET /api/v3/dashboard` 的 `summary.sections.host_watchdog` 返回 `data`、`updated_at`、`error`，其中安全数据为：

| 字段 | 含义 |
|---|---|
| `configured` | 中心配置了宿主客户端，不证明服务正在运行 |
| `available` | 本次摘要生成能够读取宿主状态 |
| `fresh` | 实际宿主观测在当前前 45 秒至后五秒内 |
| `status.checks` | 四项独立组件检查，各自带观测时间、状态、原因和耗时 |
| `status.environment` | 宿主系统、内存、运行时间、文件系统容量及 inode；缺失保持未知 |
| `status.frozen`／`reason` | 通知配置或恢复核验是否冻结，不代替组件健康结论 |
| `status.pending` | 宿主 `queued`／`sending` 通知数量，不是 PostgreSQL 待提交事务数 |

页面还复查每项检查时间和唯一性。缺少、重复、过期检查，旧总览、读取失败或未来时间异常均不能显示正常。`services.database_bytes` 仅为当前业务 schema 的表和索引大小，不能用于计算宿主磁盘剩余空间。真实零空间仍显示零，不改为未知。

飞书、邮箱分别要求 `notify-feishu`、`notify-email` 的真实工作器心跳；服务端健康标记基于二十秒内心跳和无错误，页面另检查观测时间。没有对应心跳，即使待发送队列为零仍显示未知。冻结时暂停发送并显示维护原因；存储本身仍按独立检查显示正常或异常。

## 完整备份和恢复保护

启用看门狗后，完整备份纳入一致性 SQLite 快照及摘要，也保留原密钥与认证支持资料。快照先核对归属和完整性，不能把活数据库文件的随意复制当成一致性备份。备份范围及隔离展开步骤见 [完整备份](V3-FULL-BACKUP.md)。

看门狗恢复只允许服务已停止、socket 不存在且目标状态库尚不存在的目录，不能用旧快照覆盖当前状态。恢复保留已消耗额度和通知尝试，清除旧观测、旧维护抑制与活动租约；中断发送改为未知，旧设置准备记录不再作为活动授权，状态标记 `restored_requires_reconciliation` 并冻结发送。重新启动本身不能解除该恢复保护，也不表示生产切换已获授权。

运行时自动备份设置仅在明确应用后生效：`backup.enabled`、`backup.time`、`backup.timezone`、`backup.keep_days`。完全缺失时保留旧宿主策略；首次显式配置时未提供项按启用、`03:00`、`UTC`、七天解释。新维护程序每分钟检查到期条件，按目标时区本地日期去重；保留天数不是原策略的备份份数。暂停自动任务不禁止受控 `backup-single` 手动完整备份；`run-single-backup` 仍遵守计划策略。旧维护包未升级时不得声称网页已改变其执行时间。

当前不把上述备份与恢复保护描述为 v2 最终增量迁移、生产冻结切换或保留新增数据回退已完成；这些属于后续独立门禁。`raw_hours/history_days` 双时序保留策略未开放，也未由本轮设置自动配置 VictoriaMetrics。
